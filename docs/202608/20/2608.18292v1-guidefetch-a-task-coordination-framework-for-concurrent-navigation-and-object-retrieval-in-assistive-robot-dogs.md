## 摘要
考虑一个机器人导盲犬引导盲人用户到可用座位，同时另一个辅助机器人狗并发地取回一杯咖啡并送到同一座位。这种场景激发了并发执行，因为导航和物体取回可以重叠。一个语法有效的大语言模型（LLM）计划仍可能违反具身约束，而看似成功的控制器运动本身并不确立任务完成。我们提出了GuideFetch，一个用于异构引导者和取回者团队并发导航与物体取回的协调框架。LLM从自然语言指令实例化一个调度条件化的四动作模式。在执行之前，机器人、技能和目标别名被规范化，提议的动作根据注册目标、机器人能力和选定调度进行验证。随后，机器人和物体状态控制顺序与并行执行。在一个匹配的2×2研究中，跨越90种场景和种子的组合（360次执行），所有180个在线LLM响应均无需回退或重放即可验证，并与相应的脚本计划匹配。对于每个规划器来源，顺序和并行执行分别实现了72/90和71/90的操作成功。在两种调度均完成的56个案例中，并行执行将平均完成时间缩短了41.3%。在此受控设置中，角色专业化和动作重叠缩短了已完成的任务，而状态检查则区分了计划有效性与已验证的任务完成。源代码将提供。

## Abstract
Consider a robot guide dog escorting a blind user to an available seat while a second assistive robot dog concurrently retrieves a cup of coffee and delivers it to the same seat. This setting motivates concurrent execution because navigation and object retrieval can overlap. A syntactically valid Large Language Model (LLM) plan may still violate embodiment constraints, and successful-looking controller motion does not by itself establish task completion. We introduce \textsc{GuideFetch}, a coordination framework for concurrent navigation and object retrieval by a heterogeneous guider and fetcher team. An LLM instantiates a schedule-conditioned four-action schema from a natural-language instruction. Before execution, robot, skill, and target aliases are normalized, and proposed actions are validated against registered targets, robot capabilities, and the selected schedule. Robot and object states then govern sequential and parallel execution. In a matched $2\times2$ study across 90 combinations of scene and seed (360 executions), all 180 online LLM responses validate without fallback or replay and match the corresponding scripted plans. For each planner source, sequential and parallel execution achieve $72/90$ and $71/90$ operational successes, respectively. Among the 56 cases completed by both schedules, parallel execution reduces mean makespan by 41.3\%. Within this controlled setting, role specialization and action overlap shorten completed missions, while state checks distinguish plan validity from verified mission completion. Source code will be available.

### 1. 核心问题与整体含义（研究动机与背景）

- **核心应用场景**：机器人导盲犬引导盲人用户到可用座位，同时另一台辅助机器人狗去取咖啡并送到同一座位。这构成了异构机器狗团队（guider + fetcher）在同一任务中并发执行导航与物体取回的需求。
- **核心研究问题**：异构机器人团队能否利用并发性（concurrency）来缩短任务时间，同时确保符号层面的任务进度与真实的、经过状态验证的任务完成一一对应？
- **两个关键挑战**：
    - **LLM计划可能违反具身约束（embodiment constraints）**：语法上有效的计划，可能将抓取动作分配给没有机械臂的机器人，或出现目标不匹配等问题。
    - **成功的控制器运动不等于任务完成**：轨迹执行得平滑、运动看起来正常，并不代表物体被成功抓起、托住并送达。例如，物体可能在运输前滑落，或并行执行中早期失败导致看似“更快”的假象。
- **核心主张**：必须将计划有效性（plan validity）、执行进度（execution progress）和任务完成（mission completion）视为三个不同的状态层次，分别处理与验证。

### 2. 方法论：GuideFetch 框架

- **整体架构**：将任务规范（LLM 规划）与机器人执行及测量完成解耦，形成“规划 → 确定性验证 → 编译 → 状态驱动执行 → 基于状态的完成验证”的流水线。
- **核心思想**：LLM 仅负责从自然语言指令实例化一个“调度条件化的四动作模式”（schedule-conditioned four-action schema），不直接控制执行；所有关键可行性校验由确定性验证器完成；任务进度和完成由具身状态（embodied state）决定。

**关键技术细节与流程**：

1. **问题形式化（能力约束任务图）**
   - 机器人集合 R = {r_G, r_F}，每个机器人具备技能集 C_i。
   - 任务词汇 A = {navigate, move, grasp, carry}，场景注册表 Ω 包含取物站 g_p、终点站 g_f、目标物体 o。
   - 规划器生成四个动作记录：v_j = (k_j, r_j, a_j, z_j, p_j)，其中 k_j 为名义依赖级别，r_j 为执行者，a_j 为技能，z_j 为目标，p_j 为参数。
   - 验证器检查动作记录是否与场景注册表、机器人能力集及所选调度一致；编译器构建依赖图 G = (V, E)。
   - 运行时每个动作有状态 q_j ∈ {pending, running, succeeded, failed}，前驱成功后才能运行后继，单机器人上并行动作需串行化。

2. **两种调度方式（核心对比）**
   - **顺序调度** P_seq：所有任务由 fetcher 完成：
     ```
     P_seq := [F:move(g_f), F:move(g_p), F:grasp(o), F:carry(o, g_f)]
     ```
     完成时间：T_seq = T^visit_F + T^return_F + T^grasp_F + T^carry_F。
   - **并行调度** P_par：无负载到访由 guider 完成，fetcher 同时开始取物分支：
     ```
     P_par := {G:navigate(g_f) ∥ [F:move(g_p), F:grasp(o), F:carry(o, g_f)]}
     ```
     完成时间：T_par = max(T^nav_G, T^move_F + T^grasp_F + T^carry_F)。
   - 两个调度保持相同的终端目标（无负载到访 g_f + 将物体从 g_p 送达 g_f），仅改变角色分配与动作重叠结构。

3. **计划生成与验证（Planning and Validation）**
   - LLM 提示词（prompt）中列出可用机器人、四种允许技能、注册目标、所选调度和要求的 JSON 格式，输出四动作模式。
   - 解析器提取 JSON 对象并规范化机器人/技能/目标别名，与场景注册表对应。
   - 验证器检查：四个期望动作齐全；执行者具备对应技能；carry 动作保留注册物体；并行计划必须在步骤 1 包含 guider 导航和 fetcher 移动；顺序计划必须包含四个有序的 fetcher 动作。任何不匹配直接拒绝，不进入仿真。
   - 脚本计划与在线 LLM 输出经过同一解析器和验证器，保证公平对比。

4. **执行与状态检查（Schedule Execution & Robot Skills）**
   - 执行器在统一仿真时钟下同时推进所有活动机器人，各分支根据自己状态事件推进；并行计划中两个初始动作同时启动，fetcher 的抓取和搬运不等待 guider 到达。
   - **Guider 技能**：使用 PPO 训练的循环策略（180 维 2D 激光雷达输入 + 11 维状态向量），辅以注册路径的航点进度屏蔽（waypoint progress shield）进行运动学根传输。到达终点站 0.20m 内即满足访问条件。
   - **Fetcher 技能**：基于 ALORE [2] 的腿控策略 + 关节空间手臂分阶段 + 世界坐标系逆运动学。重点在**抓取验证门**：
     - 抓取（grasp）：物体双侧同时接触。
     - 抬升（lift）：物体峰值抬升 ≥ 30mm。
     - 保持（retention）：1.0 秒、200Hz 采样下，保持抬升 ≥ 20mm，≥80% 帧及最后一帧保持双侧接触，目标与支撑碰撞边界间距 ≥ 5mm，物体倾斜 ≤ 17°，抓取参考点到末端执行器帧原点距离 ≤ 0.25m。
   - 仅当抓取/抬升/保持全部通过后，物体位姿才与末端执行器同步，开始辅助运输。

5. **完成检查（Completion Checks）**
   - 操作成功定义为：y_op = b_visit ∧ b_pickup ∧ b_grasp ∧ b_lift ∧ b_retain ∧ b_delivery。
   - 每个布尔变量根据控制器或仿真器状态在时间戳上真实触发；失败立即终止相关下游动作，不允许“看似快”的虚报。

### 3. 实验设计

- **仿真平台**：InternUtopia，基于 GRUtopia [29]；机器人分别为 Unitree Go2（guider）和 Unitree B2 + Z1 机械臂（fetcher）。
- **场景（Benchmark）**：三个 GRScenes 官方场景——Home（家庭）、Supermarket（超市）、Hospital（医院）。每个场景注册了机器人起始位姿、取物点、共享目标点和角色专属路径。
- **扰动设计（种子化）**：每个种子生成确定性的扰动记录，包括：机器人起始位置变化（≤10mm）、物体平移（1.5mm）、物体偏航角（0.5°）、物体质量（5.00–5.25g）、接触摩擦在窄标定范围内变化。
- **对比设计（匹配 2×2 设计）**：
    - 因子 1：规划器来源——脚本计划（scripted）vs 在线 LLM 计划（online Qwen3.5，4B 参数，本地部署）。
    - 因子 2：调度模式——顺序调度 vs 并行调度。
    - 总计：3 个场景 × 30 个种子 × 4 个条件 = **360 次独立仿真执行**。
- **公平性保障**：每个场景和种子跨四个条件严格匹配（同一扰动记录、同一控制器、同一阈值）；所有条件共用相同的规范化、验证、控制器检查点、状态检查和超时设置；失败的执行保留在成功率分母中，不重跑。
- **规划器提示设计**：每个调度使用 4 个语义等价的指令模板，在种子间轮换措辞；每次 Qwen3.5 调用均为新请求，无回退或重放记录。

### 6. 主要结论与发现

1. **所有在线 LLM 计划通过验证**：180 个 Qwen3.5 响应全部在首次请求即通过解析、能力检查和调度检查，无需回退或重放，且与脚本计划在规范形式上完全匹配（在测试模板范围内）。
2. **调度方式影响任务时间**：在两种调度均完成的 56 个案例中，并行执行平均耗时从 164.78s 降至 96.79s，平均缩短 **41.3%**（1.70× 加速）；成对均值差为 67.99s，bootstrap 95% 区间 [54.05, 82.04]s，sign-flip 检验 p < 0.001。
3. **提速来源因场景而异**：
   - Home 和 Supermarket：并行模式下总行驶距离更长（24.95m vs 22.05m；16.76m vs 14.86m），提速来自**时间重叠**。
   - Hospital：将无负载到访分配给 guider 还移除了 fetcher 的长距离往返，总行程从 68.25m 降至 40.60m，**角色重分配和动作重叠叠加**带来最大收益。
4. **成功率与瓶颈**：顺序和并行的操作成功率分别为 72/90（80.0%）和 71/90（78.9%），差异不显著；所有失败均发生在预运输操作（抓取/抬升/保持）阶段，无计划验证失败，无取物站到达失败，所有并行 guider 均成功到达目标。
5. **失败模式分类**（37 个不同失败配置）：19 例抓取参考点到末端执行器距离超限（>0.25m）；15 例保持倾斜超限（>17°）；3 例末帧双侧接触丢失（含 2 例同时超倾斜限）。

### 7. 优点（方法或实验设计的亮点）

- **概念分层清晰**：将“计划有效性”“执行进度”“任务完成”严格区分，避免以计划合理性取代实物验证，是方法论上的重要贡献。
- **验证与执行解耦**：LLM 只负责结构化动作记录生成，所有关键安全性和可行性检查由确定性验证器完成，兼顾语言灵活性与可靠性。
- **严格的成功判定门**：抓取要求双侧接触、抬升 ≥30mm、保持 1s 且多指标联合达标（接触率、间距、倾斜、末端距离），有效防止“看着成功但物体未拿稳”的假阳性。
- **公平的对比设计**：匹配 2×2 设计、共用控制器与阈值、脚本与在线计划同一管线、失败保留在分母、仅统计双方成功案例的成对耗时，使结论具有较强的内部效度。
- **基于场景几何解释收益来源**：根据三条场景中总路程与时间的变化，清晰区分了“时间重叠”与“角色重分配”两种提速机制，分析深入。
- **运行记录完整**：保存原始响应、验证结果、动作转移、终端条件和失败分类，支持失败可追溯性。

### 8. 不足与局限

- **实验覆盖受限**：仅 3 个注册场景、手动注册的固定路径、一个 4B LLM、一种固定动作清单；未涵盖未见过的指令、冲突/不可行的请求、更大的动作图谱或需重新规划的状态反馈。
- **仿真真实性有限**：背景物理与碰撞响应关闭，机器人根位移通过运动学传输实现而非动态控制；未建模人类跟随、动态障碍物和真实避障，因此“到达终点站”只是引导功能的代理指标，离真实导盲还有差距。
- **操作泛化不足**：仅测试一种轻量级带手柄物体，扰动范围窄（质量 ≤5.25g）；保留检查到运输前即停止，未验证辅助运输全程的物体自主保持，也未验证到达后的释放动作。
- **成功率瓶颈未解决**：并行与顺序的成功率接近（71 vs 72），表明调度优化仅带来时间收益，未改善（甚至略微降低）任务成功率；抓取保持是当前系统的明显短板，而这恰是实际可用性关键。
- **缺少真实世界和用户研究**：未进行真机实验、无盲人和低视力参与者的用户研究，无法评估真实感知噪声、执行不确定性、用户信任和风险感知。
- **算力与资源信息披露不足**：未报告 GPU 型号/数量、训练与推理成本，复现的硬件要求不透明。
