# Abstract 

AI agents can evolve by using feedback from task envi-ronments to revise their harnesses, the software that man-ages model inputs, tool use, memory, and execution, while keeping the underlying foundation models frozen. Recent studies focus on this process for single agents, leaving underexplored the harness evolution in Multi-agent Sys-tem (MAS), which requires coordinating harness changes across multiple agents. However, using a single global op-timizer, the straightforward extension from single agent harness evolution, faces a growing context and workload as the MAS scale increases. Access restrictions introduce further challenges: agents may be unable to share in-ternal information with a common optimizer, and some agents may lack permission to access the environment feedback which is for the entire MAS. To address these challenges, we propose HarnessNet, a framework for hier-archical harness evolution in MAS. Its basic unit, Agen-tron, consists of an evolvable forward harness, a founda-tion model, and a local optimizer that can observe and modify only that forward harness. Multiple Agentrons are orchestrated into a layered graph, and feedback is propagated backward from the task environment through the system so that each optimizer only receives node-specific information relevant to its own Agentron from downstream layer. Joint harness evolution can therefore be divided into smaller, coordinated tasks with separate contexts, without requiring every optimizer process to ac-cess all Agentron trajectories or raw environment feed-back. This reduces the context and workload handled by individual optimizers, and keeps optimizer access local. We conduct experiments on AgentBench with multiple foundation models to demonstrate the feasibility of train-ing HarnessNet. A comparison study against single global optimizer approach shows that HarnessNet achieves com-parable performance gains while respecting local privacy, with fewer tokens and less time required per optimizer call. A migration study further shows that the evolved harnesses remain effective after replacing the foundation models, suggesting the transferability. 

Keywords: Multi-agent Systems, Harness Engineering, Hierarchical Evolution 

# 1 Introduction 

The behavior of Large Language Model (LLM) based agents depends on both the underlying models and the software infrastructure [1, 2]. Agent development there-fore places growing emphasis on refining the software that organizes and directs model capabilities. This trend re-flects an emerging paradigm shift in AI system optimiza-tion: from a primary focus on model weights toward model-external components that govern system behav-ior, release or extend the capabilities attainable with a given foundation model, exemplified with prompt engi-neering [3, 4], context engineering [5, 6], and, more re-cently, harness engineering [7, 8]. Expressed in natural language and code, these software components and their revisions are directly accessible to human inspection and audit, supporting efforts to improve system security and controllability. Viewing the harness itself as an optimiza-tion target motivates harness evolution, in which task feedback guides iterative harness refinement while the un-derlying foundation models remain frozen. Recent work has explored closed-loop feedback-driven agent harness evolution as a form of agent system train-ing, but has focused mainly on single-agent harness evolu-tion [9–14], leaving joint harness evolution in multi-agent systems underexplored. In single-agent approaches that use a coding agent as the optimizer, this optimizer ana-lyzes the agent’s execution trajectories and modifies its harness based on feedback. A direct extension to multi-agent systems would assign a single optimizer the respon-sibility of analyzing all agents’ trajectories and updating their harnesses jointly. However, such a global optimizer extension faces challenges: (1) as the system scales up, this one-for-all design has a growing context and workload burden, which can degrade its performance [15–17]; (2) in scenario with distinct privacy or access constraints, agents may not be able to expose their internal trajectories to a shared optimizer [18–20], or directly access the envi-ronment feedback of the whole system. These limitations motivate a solution to joint harness evolution that decom-poses multi-agent system harness evolution into small, independently executable tasks while coordinating har-ness updates across agents, using local feedback. In each task, optimizer visibility and authority are restricted to the agent being updated and preserve local privacy and 1arXiv:2610.15221v1 [cs.AI] 10 Oct 2026 access boundary. To address these gaps, we propose HarnessNet, a frame-work of hierarchical, feedback-driven joint harness evolu-tion for multi-agent systems. Its fundamental unit, Agen-tron, couples an evolvable agent harness with a local opti-mizer instance whose visibility and authority are confined to that unit. HarnessNet organizes these units into a lay-ered supergraph and propagates unit-specific feedback hi-erarchically to coordinate local harness updates. We use an automated task-specific initialization procedure to re-duce the need for manual harness design, while persistent textual records of harness revisions and optimizer reason-ing make the evolution process auditable. Experiments on AgentBench [21] demonstrate significant improvements in task performance through iterative hierarchical harness evolution. Further migration studies show that evolved harnesses retain useful task-specific mechanisms across different foundation models. This work makes the fol-lowing contributions. 1. We introduce Agentron, an AI unit that combines an evolvable forward harness with a local optimizer instance, functioning as a building block for cascade evolvable AI systems. 2. We propose HarnessNet, which coordinates local har-ness updates through hierarchical feedback propaga-tion, achieving gains comparable to global optimiza-tion while reducing per-optimizer context and work-load, preserving local privacy and access boundaries. 3. We develop an automated task-specific initialization procedure and evaluate HarnessNet on AgentBench tasks, demonstrating the feasibility of automated ini-tialization and the effectiveness of subsequent har-ness evolution. 4. We assess the transferability of evolved HarnessNet systems through migration studies across founda-tion models. Results indicate that task-specific rules learned within agent harnesses remain jointly effec-tive on different models. 

# 2 Related Work 

## 2.1 Agent Improvement Beyond Model Weights 

Beyond the foundation model, an agent relies on semantic artifacts that shape its behavior and execution strategy. Refining these artifacts offers a way to improve agent per-formance without updating model weights. ProTeGi [22], OPRO [23], PromptAgent [24], and GEPA [25] opti-mize task instructions through iterative search and feed-back, while MemAPO [26] accumulates reusable strate-gies and failure patterns to guide prompt refinement. Context-oriented approaches include Context Language Models [27] and Agentic Context Engineering [28], com-plemented by ACON’s feedback-driven context compres-sion [29] and HiAgent’s hierarchical working memory management [30]. Reflexion [31], A-MEM [32], and Dy-namic Cheatsheet [33] improve the reuse of past expe-rience through textual reflection, memory organization, and persistent strategy accumulation. AutoSkill [34], MUSE-Autoskill [35], CoEvoSkills [36], SkillGrad [37], and MetaSkill-Evolve [38] further explore the acquisition and refinement of reusable agent skills. Together, these methods establish prompts, context, memory, and skills as targets for agent improvement beyond model weights. 

## 2.2 Agent Harness Evolution 

Agent harness evolution extends individual artifact refine-ment to the agent harness, the broader agent software in-frastructure, as the optimization target. SICA [39], Dar-win G¨ odel Machine [40], and MOSS [41] show that cod-ing agents can revise their own software to create agent substrates. Meta-Harness searches over complete harness implementations using source code, traces, and scores [9]. AHE structures harness components and execution evi-dence to support observable edits [11]. Self-Harness cou-ples model-specific weakness discovery with proposal val-idation [42]. Life-Harness [10], Continual Harness [12], and Adaptive Auto-Harness [13] further extend harness evolution to runtime interventions and non-stationary task streams. MILO [43] uses multi-agent to optimize agent harness. However, these works focus on single agent harness evolution, leaving underexplored the scenario of refining agent harnesses in multi-agent systems with end-to-end feedback. HarnessNet closes this gap by introduc-ing a joint harness evolution process through hierarchical feedback propagation and node-specific evolution. 

## 2.3 Multi-agent System Optimization 

Multi-agent system (MAS) optimization has explored agent selection, prompt refinement, and workflow search, leaving harness underexplored as an optimization scope. DyLAN [44] selects task-specific agent teams and adapts communication structures. GPT-Swarm [45] represents language agents as optimizable graphs and updates node prompts and graph connectivity, while Agentic Super-net [46] searches over query-dependent multi-agent archi-tectures. ANN [47] combines layered execution with tex-tual backpropagation to refine prompts and collaboration structures. EvolveNet [48] aggregates program adapta-tions from local deployments to improve a shared harness. MASS [49] coordinate the optimization of agent prompts and collaboration structures. MASPO [50] jointly refines agent prompts by evaluating their effects on downstream agents, whereas AgentGrad [51] uses agent-level interven-tions to identify failure sources and guide targeted prompt updates. EvoAgentX integrates prompt and workflow op-timizers [52]. Beyond these approaches, TPGO [53] repre-2sents MAS textual configurations as a Textual Parameter Graph and optimizes its node content and structure. Au-togenesis [54] provides versioned resource interfaces and a closed-loop protocol for managing and evolving het-erogeneous agent components. In contrast, HarnessNet deliberately makes executable agent harnesses as the op-timization object, coordinating local revisions to jointly optimize execution strategies, input-output handling, and memory management on different agent harness.

## 3.1 Agentron & HarnessNet 

3.1.1 Agentron 

We introduce Agentron, a harness-based evolvable AI unit whose evolution is driven by execution trajectories and feedback. It is defined as 

A = ( m, h, O),

which contains three components: (1) a frozen Large Language Model (LLM) m, which serves as the foun-dation model and provides reasoning capability through text; (2) a modifiable Forward Harness (FH) h, which orchestrates interactions with the model and defines the unit’s local behaviour, including context processing, tool use, and input-output handling; and (3) a frozen opti-mizer O, an independent coding agent that analyzes exe-cution trajectories, modifies the harness at the code level, and, when applicable, generates feedback for upstream units based on the resulting harness changes and the up-stream inputs recorded in the trajectories. An Agen-tron can receive messages from multiple upstream units and transmit outputs to multiple downstream units. Its harness determines how incoming information is selected, transformed, and aggregated, while its optimizer can gen-erate feedback for different upstream units. This design supports building of cascade systems composed of multi-ple Agentron units through sequential stacking or parallel branching, with the task environment as both the starting point and the endpoint.

## 4.3 Ability Migration 

We assess harness transferability by replacing Qwen3.5-9B [57] in the trained 4-node ALFWorld HarnessNet with either Ornith1.5-9B [59], an open-source model fine-tuned from Qwen3.5-9B, or Gemma4-8b-e4b [58], an open-source model from a different family. We evaluate the migrated harness checkpoints on the same validation set during training process. As shown in the upper panel of Figure 5, both replacement models benefit from the harnesses evolved with Qwen3.5-9B and exhibit similar performance improvement trends across checkpoints. We then select FH starred based on validation performance and evaluate it on the same test set. All three models fail most test case in the Model-only setting. With the evolved 4-node harnesses, however, Gemma4-8b-e4b and Ornith1.5-9B achieve success rates of 68.81% and 49.54%, which coheres with the results observed with Qwen3.5-9B. These results indicate that task-specific mechanisms learned within individual HarnessNet harnesses remain jointly effective across foundation models, including mod-els from a different family. In the hier-archical backward process, each Agentron uses its local optimizer to update its forward harness based on node-specific feedback from the downstream layer. By contrast, the global optimizer approach uses a global optimizer, implemented as an independent optimizer instance while disabling other Agentron local optimizers. We examine whether the performance gains reflect reusable task-specific mechanisms encoded in the evolved harnesses rather than memorized answers to training tasks. We analyze the 4-node ALFWorld experiment with Qwen3.5-9B [57], shown in the upper-right panel of Fig-ure 4. The foundation models remain frozen, and all up-dates are confined to the forward harness repositories. This makes the evolution process directly inspectable. We divide the process into four stages based on the training and validation curves; stage headings report checkpoint validation pass rates. 

FH0 Initialization. The initial HarnessNet uses a 4-node topology with the following role division: 

• Input Node: Organizes the task, current observa-tion, interaction history, and admissible actions for the downstream. 

• Hidden NodeA: Independently analyzes which ac-tions are currently feasible and check their precondi-tions. 

• Hidden NodeB: Tracks goal progress and recom-mends the next useful transition toward task com-pletion. 

• Output Node: Reconciles the two hidden-node analyses and selects one action from the current ad-missible set. At FH0, these nodes contain only general role prompts and forwarding logic. They do not have explicit mech-anisms for loop prevention, object-state tracking, multi-object progress, or search planning. 

FH0 (19.05%) → FH1 (33.33%). Training and val-idation performance improve sharply in this stage. Un-reliable environment interaction is the main FH0 failure mode: 25 of the first 40 failed cases terminate with invalid actions. Updates in FH1 include: 

• Input Node: Preserves the latest observation and records held objects and searched locations. 

• Hidden NodeA: Add detects for repeated information- gathering actions to prevent step waste. 

• Hidden NodeB: Add canonical actions recom-mending and starts tracking object count, transfor-mation state, and add the one-object inventory con-straint. 

• Output Node: Converts malformed suggestions into canonical commands, rejects unavailable ac-tions, and resolves conflicts using current environ-ment evidence. These changes establish more reliable multi-step inter-action with the environment. Invalid-action failures de-crease from 25 to 5 in the next failure batch, shifting the main bottleneck from action validity to long-horizon task completion. 

FH1 (33.33%) → FH4 (38.10%). Performance improves gradually and non-monotonically. FH1 often searches while already holding the target, confuses simi-lar object names or action meanings, and allows old his-tory to override the latest location or inventory. Updates through FH4 include: 

• Input Node: Introduces aGoal →Now →Progress →Next → Later structure to organize state and action order. 

• Hidden NodeA: Uses the latest location and inven-tory as state and checks immediate action precondi-tions. 

• Hidden NodeB: Preserves completed deliveries, tracks held and distinct object instances, and re-quires observed evidence before marking transforma-tions complete. 

• Output Node: Uses current state and action his-tory to avoid cycles and unnecessary search or ac-tions. By FH4, all 40 failures reach the step limit rather than terminating with invalid actions. Ten cases make par-tial pickup, transformation, or placement progress, while the other 30 perform valid but overly long searches. Thus, training reduces state and action errors but exposes search efficiency as the next bottleneck. 

FH4 (38.10%) → FH5 (76.19%). This stage yields the largest training and validation gains. All 40 FH4 fail-ures reach the step limit, and 16 cases repeatedly search locations of the same kind instead of trying another plau-sible source. Updates in FH5 include: 

• Input Node: Learns source-family priors for com-mon target objects and switches families after re-peated misses. 

• Hidden NodeA: Detects search stagnation and proposes an unvisited location from a different plau-sible family. 

• Hidden NodeB: Refreshes its plan from the lat-est visible objects and visited locations, prioritizing visible targets and avoiding unsupported locations. 

• Output Node: Remains unchanged. In the next 35-case failure batch, no trajectory visits three or more distinct locations from one family consecutively before switching families. This greatly improves the train-ing/validation performance. 

FH5 (76.19%) → FH7 (83.33%). Performance im-proves from FH5 to FH6 and then saturates, with no fur-ther validation gain at FH7. Remaining failures include leaving plausible source locations too early, attempting 9remote examination, repeating stale destinations, treat-ing proposed actions as completed, and selecting the same object instance again. Updates through FH7 include: 

• Input Node: Prioritizes unvisited sources and stops repeating ignored destinations. 

• Hidden NodeA: Distinguishes proposed actions from executed actions, and produces feasible action analysis. 

• Hidden NodeB: Tracks completed deliveries and individual object instances, avoids stale search loca-tions, and includes required steps such as opening an appliance before using it. 

• Output Node: Uses NodeA’s feasibility analysis to correct NodeB’s plan when a prerequisite is missing. These changes refine search ordering and multi-step exe-cution, producing the smaller improvement from FH5 to FH6, while FH7 maintains the same validation pass rate. Overall, the evolution process preserves the FH0 node roles while adding complementary ALFWorld-specific mechanisms inside each node forward harness. The fi-nal harnesses contain neither case IDs nor stored case-specific action sequences. Moreover, the best evolved checkpoint improves independent test performance from 16.51% at FH0 to 69.72% at FH6 (Table 4). These obser-vations support the interpretation that HarnessNet learns reusable interaction rules rather than memorizing train-ing answers.

## A.1 Frozen inputs and visibility boundary 

Before initialization starts, the controller freezes the public benchmark profile, LLM-backend profile, topology, harness contract, canonical template manifest, SDK guide, and model controls. The public benchmark profile may describe the task family, action or output schema, scoring semantics, and available tools, but it does not expose selected cases, case identifiers, observations, answers, or case-level statistics. This boundary prevents the initializer from encoding benchmark instances into FH0. Each Agent is materialized as an independent Git repository from the same canonical harness template. The topology fixes node identities, layer positions, edges, and first- and last-boundary roles. The stable Contract 1.2 runtime supplies one backend call per node invocation, preserves the complete case-local native-message history, structurally projects a single native tool call when present, and propagates execution errors through a stable error envelope.

The two selected ALFWorld experiment groups contain byte-identical public profiles. 16 A.3 Three-stage protocol 

PLAN. The controller publishes one immutable planning job for the complete network. The planner reads only registered public inputs and produces a schema-valid, function-level initialization plan. For every node, the plan specifies its role, boundary behavior, prompt-level inductive bias, authorized tool exposure, error behavior, and acceptance checks. It cannot inspect benchmark cases, modify an Agent repository, alter the frozen topology, or request changes to the fixed runtime mechanisms. 

BUILD. After the plan is accepted, the controller materializes one repository per node and publishes an independent build job for each node. A builder may specialize only ROLE.md , prompts/system.md ,

src/harness agent/tools.py , tests/test smoke.py , and the allowlisted role metadata. In particular, the fixed 

strategy.py , memory.py , and parsing.py files remain unchanged. Each successful build creates at most one com-mit and runs the job-published checks from their exact working directories. The controller then performs its own schema, repository, provenance, test, and contract validation. 

REPAIR. If network validation reports a node-local failure, the controller publishes a repair job with the structured failed checks, the frozen validation report, and the corresponding probe requests and responses. Repair preserves the original node specification and may touch only the same builder-owned paths. It may not add dependencies, weaken tests, modify the fixed runtime, invent fallback actions, or convert execution failures into successful outputs. After each repair round, the controller revalidates the network. Initialization becomes ready when all checks pass; after at most three repair rounds, remaining failures produce a terminal failed result. 

## A.4 Execution and acceptance separation 

Every initializer job is executed by a fresh Codex CLI process with frozen model controls. The captured templates require the gpt-5.6-sol model, high reasoning effort, and standard mode. Model output is not itself an accepted checkpoint: the controller independently verifies the result envelope, registered artifacts, allowed file changes, commit shape, test results, and end-to-end contract probes before recording the node commit in FH0. Raw execution traces and the controller-derived acceptance evidence are retained separately.

27 E.3 Optimizer Prompt Templates 

The templates below follow the latest semantic-report prompt wording in the Dev implementation for each op-timizer architecture. To match the comparison-study jobs, their execution controls are fixed to gpt-5.6-sol ,

reasoning effort=high , and mode=standard . Apart from these study-specific control values, the template text is reproduced verbatim; line wrapping and continuation indentation are adjusted only for typesetting. Per-job ren-dered prompts additionally append the adopted replay/history protocol and the job-specific identifier and manifest path. Listing E1: Hierarchical optimizer semantic-report prompt template. 

# Hierarchical node optimizer: semantic report Execute only the frozen ‘gpt-5.6-sol‘, ‘reasoning_effort=high‘, ‘mode=standard‘ job using ‘delivery.protocol=semantic-report-v1‘. Enforce ‘strict_local_visibility‘: read the registered local failure bundles, direct downstream feedback, environment feedback when provided, checkpoint and fixed contract. The rendered prompt is read-only. Inspect ‘case_memory_snapshot‘ when diagnosing history or memory-continuity failures; do not inspect peer or non-neighbor private traces. Before choosing a repair, systematically review the entire failure batch visible to this job. Check every case’s feedback and key behaviors first, then inspect relevant traces and implementation more deeply by failure pattern. This does not require expanding every full model trace. Distinguish observed symptoms, root cause hypotheses and supporting evidence; do not force all failures into one explanation or stop the survey at the first easy fix. Prioritize one or more patterns by their coverage, severity, strength of causal evidence, likely transfer to similar tasks and feasibility within the frozen budget. Frequency alone does not determine importance; no numerical scoring formula is required. Aim to improve the harness’s general capability on similar tasks, beyond correcting isolated cases or passing selected replay samples. A single round need not resolve every pattern. In the existing diagnosis, briefly summarize the main patterns, their supported scope and representative case IDs, why the selected targets deserve priority, and the validation findings and remaining uncertainties. Use existing tests and any adopted replay protocol to check the chosen solution. Distinguish observed local gains from expected broader benefits and note untested patterns and potential regressions. Do not create separate diagnostic reports or new report fields for this survey. Distinguish four boundaries when choosing a repair: - Fixed interfaces: preserve the fixed SDK, entrypoint, identity, request/response contract, authorized tool interfaces and execution-error propagation. - Execution constraints: obey the frozen job’s model and call budgets, visibility, read/write paths, commit limits, validation and any adopted replay protocol. - FH0 initialization limits: requirements for a neutral minimal baseline and initializer restrictions on template edits govern initialization. They do not freeze optimizer-trainable mechanisms after initialization. Continue to honor the fixed contract; existing README/ROLE descriptions of baseline behavior do not independently make an allowed implementation path immutable. - Trainable decision mechanisms: repository ‘allowed_paths‘ are trainable paths. Changes to role definitions/descriptions and prompts, as well as code-level changes to strategy, memory, parsing or tools, are permitted where declared. Choose the mechanism from the observed failure evidence; the FH0 role split is not immutable, but fixed topology, interfaces and tool permissions remain binding. When needed to address the prioritized failure patterns, you may change or replace existing mechanisms, restructure trainable code, or introduce a new mechanism or design within those paths and boundaries. Existing code need not have an implementation bug to justify a code-level decision-policy improvement. Prefer the smallest change necessary to address the failure mechanism, not the fewest edited files or a prompt-only fix. Do not require a prompt attempt before considering code, or change code merely to increase the number of code edits. Keep the optimized harness’s forward input context and node outputs lightweight while preserving decision-critical information, honoring the fixed contract and achieving the intended mechanism improvement. Avoid redundant information injection, unnecessary expansion of history or evidence, and accumulating verbose rules or intermediate explanations. Pass only the information the downstream consumer needs to fulfill its role. Consider both input and output costs, including downstream reuse and accumulation in later history. Additional context or output should have a clear mechanism benefit. This is an optimization preference, not a hard token limit or a new acceptance criterion. Never discard key constraints, evidence, uncertainty or required history merely to reduce tokens; continue to obey the frozen history contract. Create at most one candidate commit based on the published base, run necessary development tests, and leave the candidate clean. Use the interpreter provided by the controller, with the candidate repository as the test cwd. For ‘no_change‘, leave HEAD at the base without an empty commit. Keep the fixed contract and all model, visibility and commit limits. Keep test source files in their registered allowed paths. Put test-generated temporary files under the job-specific ‘Dev/tmp/‘ directory given in the launch instruction. When running pytest from the candidate repository, pass that directory as ‘--basetemp‘; do not create test temporary directories inside the candidate repository. The runner owns cleanup of its job-specific directory. The semantic report is the only final deliverable; this does not prohibit the authorized candidate edits/commit, development tests, or adopted replay input files and controller replay commands. Complete those steps before writing one JSON report to ‘delivery.report_path‘, following ‘delivery.report_schema‘. Successful reports contain ‘schema_version="1.0"‘, ‘job_id‘, ‘status="succeeded"‘, ‘diagnosis‘, ‘evidence_case_ids‘, ‘consumed_environment_feedback_ids‘, one ‘agent_decisions‘ entry, ‘consumed_downstream_feedback_ids‘, and ‘upstream_feedback‘. The decision names ‘agent_id‘, ‘outcome‘ (‘changed‘ or ‘no_change‘), ‘change_summary‘, and its own ‘evidence_case_ids‘. Evidence case lists must be nonempty, unique subsets of the visible cases. Confirm 

28 consumption of every declared environment and downstream feedback; use environment case IDs and downstream feedback IDs. Keep diagnosis and summaries brief and evidence-based. Provide exactly one upstream feedback entry per direct recipient, even for ‘no_change‘. Each entry has ‘recipient_agent_id‘, ‘feedback_type‘, ‘case_ids‘, ‘summary‘, ‘improvement_points‘, and ‘preserve_points‘. ‘improve‘ requires improvement points; ‘preserve‘ requires preserve points and no improvement points; ‘no_special_guidance‘ has neither. Explain useful upstream input without single-point blame or claims of single-node causality for an end-to-end failure. If unable to finish, write only ‘schema_version‘, ‘job_id‘, ‘status="failed"‘, and a nonempty ‘error‘. After the candidate, necessary tests and report are complete, finish immediately. The controller owns declared delivery checks, diff capture, hashes, inventory, execution statistics and full result generation. Do not generate those artifacts, write a schema checker, invoke acceptance, activate a checkpoint, or retry the job.
